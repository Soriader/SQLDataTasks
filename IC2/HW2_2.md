# HW2.2 — Design Snowflake vs Star

## Comparison / Explanation

In a Star Schema, the book category is stored directly as an attribute of `dim_book`.
Because of that, the query for revenue by category by month requires fewer joins and is easier for analysts to write.

In a Snowflake Schema, the category is normalized into a separate `dim_category` table.
This reduces redundancy and makes category management cleaner, but the query becomes longer because it needs an additional join from `dim_book` to `dim_category`.

Star Schema = fewer joins, more redundancy, simpler analytical queries.
Snowflake Schema = more joins, less redundancy, more normalized model.

---

## Star Schema Design

### Fact Table

* `fact_order_line`

### Dimensions

* `dim_customer`
* `dim_book`
* `dim_date`
* `dim_promotion`

In the Star Schema version, the category is stored directly in `dim_book` as an attribute, for example `genre`, `category_name` or `subcategory_name`.

Logical structure:

```text
fact_order_line
    -> dim_customer
    -> dim_book
    -> dim_date
    -> dim_promotion
```

---

## Snowflake Schema Design

### Fact Table

* `fact_order_line`

### Dimensions

* `dim_customer`
* `dim_book`
* `dim_category`
* `dim_date`
* `dim_promotion`

In the Snowflake Schema version, the category is separated from `dim_book` into a separate `dim_category` table.
The `dim_book` table contains `category_key`, which references `dim_category`.

Logical structure:

```text
fact_order_line
    -> dim_book
        -> dim_category
    -> dim_customer
    -> dim_date
    -> dim_promotion
```

---

## Query: Revenue by Category by Month — Star Schema

In this bookstore model, `genre` is treated as the book category.

```sql
SELECT
    d.year,
    d.month,
    d.month_name,
    b.genre AS category_name,
    SUM(f.line_total) AS revenue
FROM gold.fact_order_line AS f
JOIN gold.dim_date AS d
    ON f.date_key = d.date_key
JOIN gold.dim_book AS b
    ON f.book_key = b.book_key
GROUP BY
    d.year,
    d.month,
    d.month_name,
    b.genre
ORDER BY
    d.year,
    d.month,
    b.genre;
```

In the Star Schema query, the category is available directly in `dim_book`, so the query needs only two joins: one to `dim_date` and one to `dim_book`.

---

## Query: Revenue by Category by Month — Snowflake Schema

```sql
SELECT
    d.year,
    d.month,
    d.month_name,
    c.category_name,
    SUM(f.line_total) AS revenue
FROM gold_snowflake.fact_order_line AS f
JOIN gold_snowflake.dim_date AS d
    ON f.date_key = d.date_key
JOIN gold_snowflake.dim_book AS b
    ON f.book_key = b.book_key
JOIN gold_snowflake.dim_category AS c
    ON b.category_key = c.category_key
GROUP BY
    d.year,
    d.month,
    d.month_name,
    c.category_name
ORDER BY
    d.year,
    d.month,
    c.category_name;
```

In the Snowflake Schema query, the category is stored in a separate `dim_category` table.
Because of that, the query requires an additional join from `dim_book` to `dim_category`.

---

## Final Comparison

| Area               | Star Schema                     | Snowflake Schema                                 |
| ------------------ | ------------------------------- | ------------------------------------------------ |
| Category location  | Stored directly in `dim_book`   | Stored in separate `dim_category`                |
| Number of joins    | Fewer joins                     | More joins                                       |
| Query complexity   | Simpler                         | More complex                                     |
| Redundancy         | Higher                          | Lower                                            |
| Normalization      | Lower                           | Higher                                           |
| Analyst experience | Easier to query                 | Requires more understanding of relationships     |
| Best use case      | BI reports and simple analytics | Cleaner category hierarchy and better governance |

## Conclusion

The Star Schema version is easier for analysts because the category is stored directly in `dim_book`, which makes the revenue by category by month query shorter.

The Snowflake Schema version is more normalized because the category is moved into `dim_category`. This reduces redundancy and makes category management cleaner, but the analytical query becomes longer because it requires one more join.
